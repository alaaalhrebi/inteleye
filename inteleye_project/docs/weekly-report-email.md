# إشعارات التقرير الأسبوعي — مسودة محلية

تحديث لاحق منفصل: [المرحلة الأولى من تجربة التقرير الأولي](initial-report-experience.md) توسّع مشاهدة التجربة إلى التقارير الأولية المكتملة أيضًا عبر migration جديدة؛ ولا توسّع إرسال البريد في هذه المرحلة. الوصف أدناه يخص تنفيذ إشعارات الأسبوعي الأصلي.

## النطاق

تقرير أسبوعي مكتمل → Execute Sub-workflow → Gmail. لا توجد جدولة أو Webhook عام في Workflow البريد.
التجربة السارية وBasic تستقبلان إشعار الجاهزية فقط؛ Pro وEnterprise الساريتان تستقبلان أيضًا الحالات عالية/حرجة الخطورة والسلبية أو الشكاوى الفعلية. الحساب المنتهي لا يستقبل البريد.

المنتج المرفق ينشئ تقريرًا لكل نطاق منصة/فرع، وليس تقريرًا موحدًا للحساب. الإرسال مرة لكل تقرير محفوظ؛ قد تصل عدة رسائل أسبوعية لحساب متعدد المنصات. لم نضف تجميعًا جديدًا أو نغيّر حدود الباقات.

## ما تم إعداده

- `n8n/workflows/platform-reports.json`: نسخة من الملف المرفق، غير مفعلة؛ تستدعي البريد بعد Upsert ناجح لتقرير weekly/completed. تستخدم سياق الحلقة الحالية و`$input.all()`، وتستبعد الاشتراكات المنتهية والتحليلات غير المكتملة. تحفظ الحالات الخطيرة الأصلية داخل stats، بدل الاعتماد على حالات قد يخترعها الملخص. تحمي Webhook تحديث التقارير باعتماد Header Auth المشترك المشار إليه في Workflow سحب Google.
- `n8n/workflows/weekly-report-email.json`: مُشغِّل داخلي، يقرأ التقرير ومهمة الإرسال والعميل من Supabase، ويحجز pending → sending بتحديث مشروط. البريد نص عادي، ولا يرسل إلى الإدارة بدل العميل. لا يعيد Gmail تلقائيًا.
- Migration جديدة: سجل `report_email_notifications` ومحفز إدراج المهمة في معاملة اكتمال التقرير. لا backfill. RLS وصلاحيات تمنع العميل من الكتابة أو قراءة سجل التسليم.
- صلاحيات العرض: التجربة السارية تشاهد weekly/completed فقط عبر صفحة التقارير وGET API وRLS، ولا تُحمّل طلبات التقارير المخصصة لها. الإنشاء المخصص بقي Pro/Enterprise.

## حالات التسليم

- `pending`: لم يحجزها مُرسل بعد.
- `sending`: حجز ذري؛ لا يستطيع مُرسل ثانٍ أخذها.
- `sent`: عاد Gmail بمعرّف رسالة وحُفظت النتيجة.
- `failed`: رفض HTTP نهائي معروف عند توفر رمزه؛ لا إعادة تلقائية.
- `unknown`: لا يمكن حسم نتيجة Gmail؛ لا إعادة تلقائية.
- `skipped`: اشتراك غير مستحق أو بريد غير صالح.

إذا توقف التنفيذ بعد الحجز أو فشل حفظ نتيجة Gmail، قد يبقى `sending`. لا نحرره بمرور الوقت. راجع Gmail Sent برقم التقرير قبل أي إعادة، ثم أعد التنفيذ الداخلي بعد اعتماد إعادة المهمة المؤكدة إلى pending. لا يحتاج التعافي إعادة إنشاء التقرير أو التحليل.

إن توقف مولد التقرير بعد حفظه وقبل الاستدعاء، تبقى المهمة pending. يمكن استدعاء Workflow البريد بمعرّف التقرير من n8n يدويًا بعد التحقق؛ لا توجد عملية polling للإصلاح التلقائي.

Gmail لا يضمن exactly-once عبر الشبكة. الحجز يمنع التزامن، والقيد يمنع إنشاء مهام مكررة، والحالات الغامضة تُترك للمراجعة بدل إعادة إرسال قد تكرر البريد.

## التطبيق بعد موافقة منفصلة

1. تحقق SELECT فقط من أنواع reports.id وclients.id (bigint)، ومن سياسة reports الحالية ووجود private وauth.uid، ومن النسخة الاحتياطية. fixture الاختبار ليس نسخة كاملة من إنتاج Supabase.
2. طبّق Migration كاملة داخل BEGIN/COMMIT في وقت قليل النشاط؛ قد تنتظر أقفالًا على reports/clients. لا تغيّر أي Migration قديمة.
3. انشر تغييرات صلاحيات Next.js بعد Migration. الأسعار والدفع والتقارير المخصصة لم تتغير.
4. استورد Workflow البريد وتحقق من Credentials Supabase وGmail OAuth داخل n8n. الملف يحتوي مراجع Credentials، ولا يحتوي قيمها. لا حاجة إلى جدولة أو URL للبريد.
5. استورد نسخة Workflow التقارير غير المفعلة. في `Send Weekly Report Notification` اختر Workflow البريد بدل `SELECT_WEEKLY_REPORT_EMAIL_WORKFLOW_ID`.
6. هذا مولد الأسبوعي/الأولي المرفق، وليس Workflow الطلبات المخصصة. لا تستبدل متغير `N8N_REPORT_WEBHOOK_URL` الخاص بالتقارير المخصصة به تلقائيًا. اربط Header Auth الخاص بتحديث التقارير بالاعتماد الذي يطابق `N8N_REPORT_WEBHOOK_SECRET` وترويسة التطبيق؛ المصدر المرفق كان يفتقد مصادقة Webhook، والمسودة تستخدم مرجع الاعتماد المشترك من سحب Google. تحقق من المتصلين بهذا Webhook قبل التفعيل حتى يرسلوا الترويسة الصحيحة.
7. بعد موافقة إرسال منفصلة، اختبر تقريرًا افتراضيًا وبريدك وحده. تحقق من Gmail message ID وsent ومن وصول الرسالة، ثم اختبر نسخة Trial وBasic وPro وEnterprise. النسختان محفوظتان active=false لمنع تشغيل مجدول عند الاستيراد.
8. بعد اعتماد النتائج، أوقف Workflow التنبيهات القديم قبل تفعيل المولد المعدل؛ وإلا قد تستمر رسائله المستقلة. لا تمس Workflows سحب المنصات الأربعة.

Execute Sub-workflow بعد حدث حقيقي يتجنب آلاف تنفيذات polling الخالية. لم نغيّر جدولة مولد التقرير الأصلية. احتساب تنفيذ الـsub-workflow يعتمد على خطة n8n الفعلية.

## التراجع

أوقف مسار إرسال البريد في n8n أو استعد مولد التقرير السابق أولًا. لا تحرر sending/unknown ولا تحذف سجل التسليم؛ القيد يحافظ على عدم تكرار الرسائل عند العودة. عند التراجع عن عرض الأسبوعي للمجاني، استعد ملفات Next.js السابقة، ثم استخدم ملف rollback بعد موافقة مستقلة. يحتفظ rollback بجدول التسليم وبياناته، ويزيل المحفز والسياسات المضافة فقط.

بعد هذا التراجع لا تعِد تشغيل Migration كاملة عشوائيًا، لأن جدول التسليم المحتفظ به سيظل موجودًا؛ إعادة التفعيل تحتاج استعادة المحفز والسياسات فقط بعد المراجعة.

تفعيل الأسبوعي للمجاني تغيير مقصود بصلاحيات العرض؛ لا يفتح الأولي أو المخصص للمجاني ولا يغيّر السعر أو الباقة. التقارير الحالية لا تُعدل أثناء Migration.

نتيجة التنفيذ المحلي: 132 اختبارًا ناجحًا، صفر فشل أو تخطٍ. نجح TypeScript والبناء وفحص Workflows سحب المنصات الأربعة. بقي ESLint متعطلًا بسبب غياب الإعداد السابق، ولم نضف إعدادًا أو مكتبة خارج النطاق.
