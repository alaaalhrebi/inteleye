# تقرير دورة الدفع ودمج Payment Intents

الفرع المحلي: `feat/moyasar-payment-cycle`. لا Commit أو Push أو Merge أو Deploy، ولا Migration على الإنتاج ولا دفعة حقيقية. اختبارات SQL استخدمت PostgreSQL 16 مؤقتًا مع `--network none` وحسابات صناعية. استجابات الدفع في اختبارات المتصفح محاكاة بالكامل.

## النتيجة

تم دمج مكتبة ميسر الرسمية `moyasar-payment-form@2.3.0` مع إنشاء/استعادة Payment Intent من الخادم عند `on_initiating`، قبل إرسال البطاقة من المتصفح مباشرة إلى ميسر. لا تمر بيانات البطاقة بخادم IntelEye.

الدفع لا يتفعّل من حالة Intent `fulfilled`؛ يلزم جلب عملية الدفع نفسها والتحقق من `paid` والمبلغ والعملة والطلب. لا يُصدر Intent بديل لمحاولة منشورة غير محسومة، ولا تسمح مهلة الطلب المحلية بإعادة التحصيل.

الأسعار دون تغيير: Basic 199 ريال، Pro 499 ريال، Enterprise 999 ريال. الاشتراك الجديد شهر تقويمي من أول تفعيل؛ الترقية بفرق السعر الحالي وتحتفظ بتاريخ الانتهاء. الحساب النشط دون انتهاء يحتاج مراجعة قبل الترقية. لم تتغير الباقات وحدودها أو n8n أو التقارير أو حرية الروابط. شبكات البطاقة الأربع السابقة محددة صراحة: Visa وMastercard وmada وAmex، تجنبًا لتغيير defaults في الإصدار الجديد.

## سلوك الاستعادة ومنع التكرار

| الحالة | التصرف |
| --- | --- |
| لا توجد محاولة | إنشاء Intent عند ضغط الدفع فقط، ثم حفظ معرّفه قبل تسليم السر للعميل. |
| Intent `created` وصالح | استعادة Intent نفسه؛ يستطيع العميل متابعة الدفع بعد إغلاق الصفحة. |
| Intent `fulfilled` | البحث عن العملية ببيانات الطلب والمحاولة، ثم GET للعملية نفسها. لا يعتبر fulfilled نجاحًا. |
| العملية `paid` | حفظها وتفعيل الاشتراك ذريًا؛ إعادة الطلب لا تعيد التفعيل أو تمدد الانتهاء. |
| العملية `initiated` أو `authorized` أو غير محسومة | منع تحصيل جديد مع رسالة انتظار واضحة. |
| العملية `failed` أو `voided` مؤكدة | السماح ببديل، لأن Intent السابق استُهلك ولا يمكن استخدامه مرة أخرى. |
| Intent `canceled` | السماح ببديل بعد تأكيد الحالة من المزود. |
| Intent غير مستخدم ومنتهٍ | يتطلب قراءة حالة `created` ووقت المزود وتاريخ الانتهاء؛ الساعة المحلية وحدها لا تحرره. |
| API غير متاح أو معرّف العملية لم يظهر في البحث | لا ننشئ بديلًا، ولا نفترض الفشل من قائمة فارغة أو 404. |

تستخدم الحجوزات `intent_generation` و`intent_reserved_at` و`intent_id`. الحجز الذري تحديث مشروط على إصدار الحجز والحالة والمعرّف. بعد 30 ثانية يمكن استعادة حجز **إنشاء غير منشور** فقط: نتحقق ذريًا أن معرّف Intent لم يُحفظ، ونغيّر إصدار الحجز؛ أي استجابة متأخرة لا تستطيع حفظ معرّفها أو تسليم سرها. مرور الوقت يسمح بمحاولة الاستعادة، لكنه ليس إثبات عدم الدفع.

إذا ضاعت استجابة قاعدة البيانات بعد حفظ معرّف Intent، يعود العميل إلى المعرّف المحفوظ نفسه. إذا أُنشئ Intent لدى المزود دون أن يصل ردّه، قد يبقى Intent مهجور لدى ميسر؛ لا يُسلّم سره للمتصفح، ولا يسمح العامل القديم بتسليمه بعد تغيير إصدار الحجز. ينتهي لدى المزود دون تحصيل من هذا التدفق.

سر `client_secret` خاص بمحاولة واحدة ويُرسل في JSON للمستخدم المسجل صاحب الطلب، بعد الحفظ، مع `private, no-store`. لا يُخزّن في جدول الطلبات ولا يوضع في URL أو logs. مفتاح ميسر السري ومفتاح Supabase service role يظلان بالخادم.

## المكتبة وسلامة التحميل

التوثيق الرسمي لميسر يشير إلى حزمة npm نفسها. تحققت بصمة SHA512 لحزمة npm وتوقيعات السجل، وتطابق JavaScript وCSS في jsDelivr معها. تستخدم الصفحة ملفات UMD وCSS الأصلية المثبتة بالإصدار، دون `latest` أو تثبيت اعتماد npm جديد:

- `https://cdn.jsdelivr.net/npm/moyasar-payment-form@2.3.0/dist/moyasar.umd.js`
- `https://cdn.jsdelivr.net/npm/moyasar-payment-form@2.3.0/dist/moyasar.css`

بصمات SRI SHA384 مثبتة في الصفحة مع `crossOrigin=anonymous`. التحميل عبر `next/script` بعد التفاعل يحافظ على توافق Next.js؛ لا نستورد مكتبة تعتمد على DOM في مكونات الخادم.

## نتائج الاختبارات

**191 اختبارًا ناجحًا، صفر فاشل** في الجولة النهائية: 38 لدورة الدفع ومساراتها، 31 لـIntents، 99 اختبارًا سابقًا، 22 تشمل مجموعة PostgreSQL وحالاتها، واختبار متصفح واحد.

```bash
node --test scripts/payments.test.cjs scripts/payment-intents.test.cjs scripts/payment-intents-browser.test.cjs scripts/phase-one.test.cjs supabase/tests/payments.test.cjs
./node_modules/.bin/tsc --noEmit --incremental false
npm run check:n8n
NEXT_TELEMETRY_DISABLED=1 npm run build
```

تغطي إغلاق الصفحة وإعادة فتحها، حجزين متزامنين، ضياع رد إنشاء Intent، ضياع رد حفظه، استجابة قديمة بعد استعادة الحجز، تعذر الاتصال بميسر، انتهاء غير مستخدم، إلغاء أو فشل مؤكدين، دفع ناجح وتأخر التفعيل ثم استعادته، فقد معرّف العملية، حالات خاطئة، وإعادة Webhook/التفعيل. اختبار المتصفح أثبت أن المكتبة ترسل إلى fulfill فقط بعد on_initiating، وأن نموذج المزود المحاكى يقبل عملية واحدة ويرفض إعادة استخدام Intent، ولا يرسل بيانات البطاقة إلى مسار تحقق IntelEye.

نجح TypeScript والبناء وفحص workflows الأربعة. التشغيل المحلي للنسخة المبنية أعاد 401 لإنشاء الطلب وتهيئة Intent دون جلسة، و401 للـWebhook دون سر صحيح، و307 من checkout غير المسجلة إلى تسجيل الدخول.

اختبار المتصفح تعطل أولًا بسبب انتظار التنظيف وطريقة ملء الحقول المقنّعة؛ أُصلح runner والكتابة لتطابق أحداث كتابة المستخدم، ثم نجح ضمن الجولة الكاملة. لم تُعطّل أي assertions. `npm run lint` ما زال يطلب تهيئة ESLint بسبب غياب إعداده السابق؛ لم نضف تهيئة أو مكتبات.

اختبار المتصفح يستخدم Playwright وChromium الموجودين في البيئة، دون إضافتهما لاعتمادات التطبيق. إعادة تشغيله في بيئة أخرى تتطلب توفر أدوات المتصفح؛ ليس جزءًا من متطلبات تشغيل الموقع.

## الفحص البصري

أُجريت المقارنة على Chromium محلي عند 1440×1000 و390×844، ببيانات ومعرّفات مفاتيح صناعية وحظر طلبات المزود؛ لم يُستخدم مفتاح Live حقيقي. سُمّي أصل المعاينة HTTPS صناعيًا لإتاحة عرض شكل Live دون استدعاء بوابة الدفع.

- الكمبيوتر: عرض الملخص 425px وعرض بطاقة الدفع 575px، وارتفاعهما 466.59px في النسختين. عرض النموذج 340px.
- الجوال: عرض البطاقتين 358px؛ ارتفاع الملخص 406px وبطاقة الدفع 479px في النسختين. عرض النموذج 308px.
- اللون والخط والخلفية وملخص الباقة محفوظة، وزر الدفع بنفس `rgb(24,63,156)`، دون تمرير أفقي أو أخطاء JavaScript.
- نصوص بعض التسميات والشعار داخل نموذج ميسر تغيرت مع المكتبة الرسمية؛ لا نموذج بطاقة مخصص.

## متطلبات الإنتاج التي لم تُنفذ

لا متغيرات جديدة بسبب Intents. في Vercel Production فقط: `PAYMENTS_MODE=live`، ومفتاحا ميسر Live للحساب نفسه، و`MOYASAR_WEBHOOK_SECRET` مطابق بطول 24 حرفًا على الأقل، و`SUPABASE_SERVICE_ROLE_KEY` للمشروع الذي يشير إليه `NEXT_PUBLIC_SUPABASE_URL`، مع المفتاح العام الموجود للمشروع نفسه. `VERCEL_ENV` يحدده Vercel. الكود يرفض Test وPreview؛ المفاتيح الحقيقية غير متاحة في هذه الجلسة ولم تُستخدم.

قبل اعتماد الإطلاق:

1. مراجعة SELECT فقط لمخطط الإنتاج وأسماء الجداول والدوال وأنواع `clients` وسياساته ومحفزات الاشتراك. fixture المحلي ليس نسخة كاملة من الإنتاج.
2. تأكيد دعم Intents في حساب ميسر وإعدادات حساب التاجر. تفعيل الحساب جاء من المستخدم ولم نتصل بلوحته مستقلًا؛ خطأ Entity not activated لا يُتجاوز برمجيًا.
3. الموافقة المنفصلة على تطبيق Migration كاملة داخل BEGIN وCOMMIT، ثم نشر API وصفحات الدفع معًا. لا backfill ولا تغيير للعملاء الحاليين. إنشاء FK قد ينتظر أقفالًا على clients؛ نفّذ وقتًا قليل النشاط مع مهلة قفل مناسبة.
4. إعداد Webhook HTTPS/POST وحدث payment_paid وسر مطابق؛ فحص الوصول والحماية وزمن Vercel. لا تعتبر نجاح صفحة التأكيد إثبات وصول Webhook.
5. أي اختبار حقيقي أو تغيير إعدادات أو نشر أو Git action يحتاج موافقة منفصلة. تكامل المزود الفعلي وSupabase/PostgREST الإنتاجي لم يُختبرا.

## حدود الحماية والتراجع

الضمان يعتمد على استخدام Intent نفسه داخل التدفق الجديد وعلى تعهد ميسر الرسمي بأنه single-use. اختُبر التنفيذ محليًا بمزود محاكى؛ لم نثبت السلوك بتعامل حقيقي على حساب التاجر. لا يشمل الضمان نموذجًا قديمًا محفوظًا في تبويب أو استدعاءات Create Payment مباشرة خارج التدفق الجديد؛ يجب مراجعة الانتقال من النموذج القديم قبل الإطلاق.

عند تعذر إثبات نتيجة دفعة منشورة، يبقى التحصيل محظورًا حتى الاستعادة أو مراجعة الدعم؛ لا نحررها لمجرد مرور الوقت أو نتيجة بحث فارغة. دفعات refunded/captured وغيرها لا تُعامل كفشل قابل لإعادة التحصيل تلقائيًا. لا توجد معالجة آلية للاسترجاع بعد التفعيل أو تجديد تلقائي.

يمكن أن ينتهي Intent غير مستخدم عند المزود بعد ساعة كما في التوثيق. نتحقق من الحالة ووقت المزود قبل استبداله. عند فقد معرّف الدفع نبحث بالمعلومات التعريفية ونراجع pagination؛ نتائج مبهمة تتوقف دون خصم جديد. الطلب نفسه لا ينتهي تلقائيًا بعد 15 دقيقة إذا كانت دورة الدفع قائمة، ويمكن تغيير الباقة قبل بدء أي محاولة فقط بتحديث ذري يمنع سباق بدء الدفع؛ بعد وجود حجز أو Intent أو سجل دفع يبقى تغييرها محظورًا حتى حسم الدورة.

للتراجع بعد إطلاق معتمد: أوقف استقبال محاولات جديدة بنسخة إيقاف معتمدة وتحقق من أثرها؛ تغيير متغير Vercel وحده لا يحدّث deployment القائم. لا تستبدل النموذج مباشرة بمسار Create Payment قديم بينما توجد Intents غير محسومة. راجع/ألغِ Intents غير المستخدمة لدى المزود بعد موافقة مستقلة، واستعد نتائج أي Intents مستخدمة قبل السماح بتدفق بديل. احتفظ بالسجل المالي والجداول؛ لا تحذف دفعات ولا تعكس اشتراكات مدفوعة جماعيًا. التراجع عن تفعيل معروف يراجع منفردًا وفق السجل.
